# Диктофон стакана MEXC

Пишет публичный поток фьючерсов MEXC на диск: стакан заявок и ленту сделок,
круглосуточно, без выводов и без торговли. Нужен, чтобы на реальных данных
проверить, есть ли в стакане то, на чём можно зарабатывать, — до того, как
на это будет потрачен месяц ручной торговли.

## Отдельно от бота — намеренно

Проект не пересекается с `trading-bot` ни в чём:

| | trading-bot | этот проект |
|---|---|---|
| каталог на сервере | `/root/trading-bot` | `/root/orderbook-recorder` |
| окружение | своё `venv` | своё `venv` |
| служба | `trading-bot` | `orderbook-recorder` |
| данные | `cycles.csv` и прочее | `data/` |
| ключи API | нужны | **не нужны** |

Диктофон читает только публичные данные, ключей не знает и до счёта дотянуться
не может физически. Установка и перезапуск ничего не делают с ботом — прогон
идёт как шёл.

## Что записывается

Одна таблица parquet (zstd), каталог на сутки, файл на каждые 10 минут:

```
data/2026-08-23/events_2026-08-23T14-30.parquet
```

Почему не файл на час: подпись parquet ставится при закрытии, и открытый файл
прочитать нельзя. При часовой ротации свежий час был бы невидим для анализа, а
отчёт на работающем диктофоне падал бы. Десять минут — компромисс между числом
файлов и тем, как быстро данные становятся доступны.

| поле | что это |
|---|---|
| `ts_local_us` | когда сообщение получили мы, UTC, микросекунды |
| `ts_exch_ms` | время события по часам биржи (`cts` пачки, `t` сделки) |
| `lag_ms` | разница между ними — сырая задержка доставки |
| `symbol` | инструмент |
| `channel` | `depth` / `deal` / `snapshot` / `gap` / `clock` / `status` |
| `version` | номер последнего изменения в пачке |
| `payload` | **сырое** сообщение биржи, как пришло |

Сырой payload — сознательное решение. Если разбор где-то ошибается, записи от
этого не портятся: разбор переделывается офлайн сколько угодно раз, а
потерянные данные не вернуть.

## Что выяснилось про протокол MEXC (проверено 2026-08-23)

Три вещи, на которых такие проекты обычно ломаются молча:

**1. Непрерывность считается по `begin`, а не по шагу версии.** Каждая пачка
несёт `begin` и `end` — диапазон склеенных изменений; `version` == `end`. Поток
цел, когда `begin == предыдущий end + 1`. Шаг самого `version` произвольный —
от 3 до нескольких сотен. Если проверять его, ровный поток выглядит сплошным
разрывом (у нас так и было: 40 «разрывов» за 45 секунд на идеально целых данных).

**2. REST-снимок отстаёт от живого потока.** Пока он едет, биржа успевает
отправить ещё пачки, и его версия оказывается ниже текущей позиции стрима.
Применять снимок «как есть» и ждать продолжения нельзя — следующая живая пачка
придёт с `begin` намного больше `version + 1`, книга не соберётся никогда.
Правильно: копить пачки с момента запроса снимка и доигрывать их поверх него.
Это дало 107 «разрывов» → 5.

**3. Стакан приходит пачками раз в ~200 мс.** Биржа сама агрегирует изменения
за это окно. Тик-в-тик публичного потока нет ни у кого, кто не колокейшн.

**4. Часы меряются по самому быстрому ответу, а не по среднему.** Ошибка
оценки сдвига часов не превышает половины RTT, поэтому из нескольких замеров
берётся тот, у кого RTT минимальный. Усреднение по зашумлённому каналу давало
«сдвиг» в целую секунду на ровном месте и превращало настоящие 130 мс задержки
в мнимые 1200 мс.

Замеренная задержка доставки на канале Мак → MEXC: **медиана ~130 мс, p95 ~380 мс**
для стакана; лента примерно на 50 мс медленнее. Вместе с 200-миллисекундной
пачкой это значит, что наша картина книги отстаёт от биржи примерно на
**200–350 мс**. Не на секунды и не на минуты. На сервере число будет своё —
диктофон меряет его сам и пишет в журнал каждую минуту.

**5. Собранная книга достоверна только в ценовом диапазоне последнего якоря.**
Инкременты приходят по всей книге, но уровень, которого не было в снимке и
который с тех пор ни разу не менялся, нам неизвестен. На BTC 500 уровней — это
всего ±50 USDT, цена выходит за них за минуты. Поэтому берём 1000 уровней и
якорь раз в 120 секунд; сверка «снимок A + все пачки == снимок B» проходит
на 93–100%, остаток — как раз такие далёкие нетронутые уровни.

Глубина REST-снимка: потолок 1500, берём 1000.

### Единицы измерения — контракты, а не монеты

Объёмы в стакане и в ленте приходят **в контрактах**. Размер контракта свой у
каждого инструмента (`/api/v1/contract/detail`, поле `contractSize`):

| Символ | 1 контракт | шаг цены | «110 000» в стакане это |
|---|---|---|---|
| BTC_USDT | 0.0001 BTC | 0.1 | 11 BTC ≈ $850 000 |
| ETH_USDT | 0.01 ETH | 0.01 | 220 ETH ≈ $538 000 |
| SOL_USDT | 0.1 SOL | 0.01 | 1300 SOL ≈ $123 500 |

Без этой поправки любая оценка размера плиты промахивается в тысячи раз.
Просмотрщик тянет `contractSize` с биржи сам и показывает деньги; в сырых
записях лежат контракты, как их отдала биржа.

## Установка

**[МАК]** проверить локально:

```bash
cd ~/orderbook-recorder && python3 -m venv venv && ./venv/bin/pip install -r requirements.txt && ./venv/bin/python tools/smoke.py 60
```

**[СЕРВЕР]** забрать код и поставить службой:

```bash
cd /root && git clone https://github.com/TOPGmaloy/orderbook-recorder.git && cd /root/orderbook-recorder && bash install_service.sh
```

Установщик сам создаст окружение, прогонит проверку на 60 секунд и поставит
службу только если проверка прошла. Каталог `/root/orderbook-recorder` —
отдельный от `/root/trading-bot`, бот при установке не трогается.

**[СЕРВЕР]** обновиться после правок на маке:

```bash
cd /root/orderbook-recorder && git pull && systemctl restart orderbook-recorder
```

## Работа с ним

**[СЕРВЕР]** отчёт по записанному:

```bash
/root/orderbook-recorder/venv/bin/python /root/orderbook-recorder/tools/report.py
```

Отчёт отвечает на три вопроса, без которых считать статистику нельзя:
реальная задержка (с поправкой на расхождение часов), сколько разрывов, и
сходится ли собранная из инкрементов книга с якорными снимками.

Живой журнал: `journalctl -u orderbook-recorder -f`

## Какие пары вообще годятся

```bash
/root/orderbook-recorder/venv/bin/python /root/orderbook-recorder/tools/universe.py
```

Замер 2026-08-24 по 1019 бессрочным USDT-парам MEXC:

| спред | пар | из них оборот > $10 млн |
|---|---|---|
| ≤ 0.5 б.п. | 18 | 8 |
| ≤ 1 б.п. | 35 | 9 |
| ≤ 2 б.п. | 102 | 18 |
| > 2 б.п. | 864 | 17 |

| пара | спред б.п. | шаг б.п. | спред/шаг | $ у касания | $ в ±5 б.п. |
|---|---|---|---|---|---|
| BTC_USDT | 0.142 | 0.013 | 11.0 | 506k | 15 379k |
| ETH_USDT | 0.041 | 0.041 | 1.0 | 764k | 5 128k |
| XAU_USDT | 0.087 | 0.022 | 4.0 | 28k | 1 465k |
| SOL_USDT | 1.050 | 1.050 | 1.0 | 513k | 7 275k |
| XRP_USDT | 0.668 | 0.668 | 1.0 | 203k | 892k |

**Спред/шаг** — ключевое и неочевидное число. Ровно 1 значит, что спред уже
минимален и улучшить цену нельзя: лимитка всегда встаёт в конец очереди за всей
плитой. Больше 1 — можно встать на шаг впереди и пролезть вперёд очереди. У BTC
это 11, у ETH и SOL — 1.

Универс моментум-бота (188 пар с оборотом выше 800k) для скальпинга не годится:
медианный спред там 2.6 б.п., у четверти хуже 5.2 — при цели в 5 б.п. половина
прибыли уходит на вход и выход. **Универсы двух стратегий почти не пересекаются.**

## Посмотреть глазами

```bash
/root/orderbook-recorder/venv/bin/python /root/orderbook-recorder/tools/viewer.py --symbol BTC_USDT --minutes 8 --out /root/viewer.html
```

Делает один самодостаточный HTML: тепловая карта стакана (время по
горизонтали, цена по вертикали, темнее — больше объёма стоит), поверх неё
сделки точками (синяя — забрали по аску, оранжевая — отдали по биду), внизу
лента, справа — стакан лестницей на тот момент, куда наведён курсор.

Файл открывается локально, интернет и сторонние программы не нужны. Годится,
чтобы натренировать глаз на поглощения и сбежавшие плиты до того, как считать
статистику.

Важно: файл, в который идёт запись прямо сейчас, прочитать нельзя — у parquet
footer дописывается при закрытии. Инструменты его молча пропускают; он станет
доступен после ротации (`ROTATE_MINUTES`, по умолчанию 10 минут).

## Настройки на лету

Не правя файл, через переменные окружения:

```bash
OBR_SYMBOLS=BTC_USDT,ETH_USDT OBR_SNAPSHOT_SECONDS=30 ./venv/bin/python run.py
```

Частые якоря (`OBR_SNAPSHOT_SECONDS=30`) нужны, чтобы прогнать проверку сборки
за пару минут вместо получаса. В бою — раз в 300 секунд.

## Диск

**249 МБ в сутки** на трёх инструментах (замерено 2026-08-24). Сырьё хранится
`RETENTION_DAYS = 14` дней и чистится само — это около **3.5 ГБ** постоянно
занятого места. При остатке меньше `MIN_FREE_GB = 3` запись останавливается и
пишет об этом в журнал, а не молча забивает диск.

### Что уже сделано, чтобы было меньше

| Мера | Было | Стало | Потеря информации |
|---|---|---|---|
| `zstd` с уровня 1 на 19 | 308 МБ | 244 МБ | нет |
| снимки 1000 уровней/120 с → 250/300 с | 18.6 МБ | 1.9 МБ | нет |

Сжатие на уровне 19 стоит порядка 16 мс раз в 10 секунд — на фоне простаивающего
процессора это незаметно.

### Что НЕ помогает — проверено, не повторять

**Сменить формат на колоночный** (цены целыми тиками, объёмы int64, delta-кодирование
вместо JSON-строки). Звучит как очевидный выигрыш в разы, на деле даёт **ноль**:

```
JSON строкой + zstd-1                308 МБ/сутки
колонками + delta + zstd-12          333 МБ/сутки
```

Причина: текст стакана крайне однороден (соседние цены отличаются последними
цифрами), и zstd уже выжимает его до ~6 байт на обновление уровня. Это близко к
энтропийному пределу, колонками ниже не получается, а сложности прибавляется много.

**Отрезать дальние уровни.** Тоже кажется очевидным — и тоже почти ничего не даёт:

```
доля обновлений в полосе ±0.05% от цены   65%
                          ±0.50%          86%
                          ±1.00%          91%
```

Объём создаёт не «дальний» стакан, а сама торговля у лучшей цены. Отрезав всё
дальше ±0.5%, экономишь 14% места и теряешь возможность изучать, как ведут себя
плиты на подходе. Плохой размен.

**Разложить каналы по разным файлам.** 282 против 273 МБ — хуже из-за накладных
расходов на файл.

### Что действительно уменьшает объём

Только два рычага, оба с реальной ценой:

* **меньше инструментов** — линейно: два вместо трёх ≈ 166 МБ/сутки, один ≈ 83;
* **короче хранение** — `OBR_RETENTION_DAYS=7` вдвое уменьшает занятое место.

Правильный долгий вариант — многоуровневое хранение: сырьё держать 5–7 дней, а
посчитанные по нему признаки (лучшие цены, дисбаланс, OFI, сделки на сетке 1 с)
хранить вечно — они занимают единицы мегабайт в сутки. Делать это имеет смысл
после того, как анализ покажет, какие признаки вообще нужны.

## Чего он не делает

Не торгует, не считает сигналы, не рисует. Это диктофон. Анализ — отдельно,
по записям.
